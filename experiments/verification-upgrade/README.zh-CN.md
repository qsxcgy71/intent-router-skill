# 从“写了通过”到“检查证据”：Skill Router 改造与对比实验

日期：2026-11-07。

本轮提升集中在验证可靠性。旧记录器会检查字段、状态和非空证据引用，新记录器会读取回执，核对被检查文件与证据文件的 SHA256 内容指纹。路由排序算法和冻结规则没有为这次改造调整，既有路由评测结果不变。

## 为什么做这些改动

现有 Router 已有路由 CLI、评测、偏好覆盖、候选发布和回退工具，因此继续复用这些机制。本轮针对诊断出的实际缺口做局部修改：

| 诊断 | 改动 | 预期作用 |
|---|---|---|
| 流程散在多处文档 | 在入口增加工作地图和按需阅读入口 | 减少查找成本；本轮未量化阅读时间 |
| 日常同步说明与冻结输入政策冲突 | 分开 map 同步与冻结目录刷新 | 避免按维护说明误改冻结输入 |
| 非空引用即可支撑“通过”声明 | 将命令结果、检查对象、回执绑定到内容指纹 | 自动发现缺失、冲突和失效证据 |
| 自动、AI、人工结论混为一个 passed | 分开三个维度，并显示未验证状态 | 避免把程序检查当作人工认可 |
| 单次反馈容易被泛化 | 显式记录 single_task / lasting_rule | 保留适用范围；记录不自动应用规则 |

公开源保留仓库已有的通用版和公开地图，只合入相关新流程、工具、样例和说明。私人的能力目录、反馈记录、机器路径、发布状态和回退快照没有上传。

## 对照与复现方法

对照是**本次改造前一刻的本地记录器**，保存在 `fixtures/pre_upgrade_recorder.py`，不是更早的 GitHub main 快照。新版来自 `murphy-skill-router/scripts/`。输入场景、期望结果和测试过程写在 `run_experiments.py` 中；`results.json` 保存源文件指纹、逐项结果和运行环境。

旧接口没有 `verification_bundle` 字段，所以旧版接收同一声明的旧格式，新版接收新格式；两边面对相同的文件状态。这样测的是验证能力，而不是旧版拒绝未知字段的能力。

在仓库根目录执行，仅需 Python 3.9+ 标准库，无网络或模型调用：

```bash
PYTHONDONTWRITEBYTECODE=1 python3 experiments/verification-upgrade/run_experiments.py \
  --output /tmp/router-comparison.json
```

数据均为合成内容，写入临时目录，结束后清理。输出位置可自行指定；不要覆盖已作为证据引用的历史结果。

## 实验一：12 个证据验证场景

期望结果按确认的验证要求定义。以下是有意构造的场景覆盖，不是随机生产样本，不能把 12/12 外推为真实场景成功率。

| 场景 | 期望 | 改造前 | 改造后 |
|---|---|---|---|
| 当前有效回执 | 接收 | 接收 | 接收 |
| 尚未验证的旧格式提案 | 接收 | 接收 | 接收 |
| 摘要含敏感内容模式 | 拒绝 | 拒绝 | 拒绝 |
| 引用回执不存在 | 拒绝 | 接收 | 拒绝 |
| 检查对象已变化 | 拒绝 | 接收 | 拒绝 |
| 回执内容已变化 | 拒绝 | 接收 | 拒绝 |
| 命令失败却声明通过 | 拒绝 | 接收 | 拒绝 |
| 新通过声明没有绑定证据 | 拒绝 | 接收 | 拒绝 |
| 检查未执行却声明通过 | 拒绝 | 接收 | 拒绝 |
| 证据路径越出指定范围 | 拒绝 | 接收 | 拒绝 |
| 总结状态与验证维度矛盾 | 拒绝 | 接收 | 拒绝 |
| AI 评估原文发生变化 | 拒绝 | 接收 | 拒绝 |

判断符合预期的场景从 **3/12 到 12/12**。10 个应拒绝场景中，无效接收从 **9/10 到 0/10**；2 个有效场景均无误拒绝。未绑定新通过声明被拒绝，是本轮明确引入的规则变化。

## 实验二：兼容与历史证据漂移

两版均通过只读预检不落盘、重复记录幂等、旧历史记录保留这三项检查。记录之后修改检查对象：旧版读取时不标明失效；新版返回 `verification_audit.binding = unverifiable`。两版均未改写历史文件。

这让“当时记录过通过”与“当前仍有有效证据”成为两个可区分的事实。

## 实验三：局部运行成本

在同一台机器上，对一个小文件和一个回执执行 dry-run，预热 10 次后测量 100 次。以下为提交结果的舍入值，复跑会波动。

| 指标 | 改造前 | 改造后 |
|---|---:|---:|
| 中位耗时 | 0.080 ms | 0.321 ms |
| p95 耗时 | 0.084 ms | 0.356 ms |

新增文件读取与哈希检查带来约 0.24 ms 的中位增量。没有速度提升；也未测试大文件、多依赖或网络文件系统的性能。

## 实验四：路由行为是否改善

`routing-comparison.json` 汇总已执行的同机、同冻结配置前后评测，含原始报告指纹。它与上面的可移植证据实验分开：完整私人目录不公开，因此仓库克隆不能独立重跑完全相同的本地 124 案例配置。

| 集合 | 改造前 Top-1 | 改造后 Top-1 |
|---|---:|---:|
| train | 24/24 | 24/24 |
| heldout | 12/12 | 12/12 |
| safety | 19/20 | 19/20 |
| regression | 44/44 | 44/44 |
| ambiguity | 12/12 | 12/12 |
| feedback | 12/12 | 12/12 |
| 合计 | 123/124 | 123/124 |

两版 Hit@3 均为 124/124；风险错误、确认漏报和不可用路线误导指标均未增加。结论是**保留既有路由表现，没有观察到路由准确率提升**。新 Skill 的 map 路由只做了三个流程案例的 AI 审阅，没有计入上述确定性评测成绩。

## 负对照：这套检查仍然信任本地证据的来源

额外构造一个未实际运行命令、但字段和指纹完全一致的假回执，两版均接收。结果保存在 `untrusted_receipt_control`。因此本轮解决的是证据缺失、版本漂移和内部矛盾，不包含回执作者认证。AI/人工判断的真实性和语义质量仍需对应评估者负责，未声明的依赖也不受指纹检查覆盖。

## 验证状态与下一轮实验

- 自动验证：公开包的 46 项反馈与证据测试通过；可移植对比脚本通过。本地完整候选另有 88 项不同测试及发布门禁通过。
- AI 评估：执行 Agent 审阅过工作地图及正例、反例、只读案例；不是独立盲测。
- 人工确认：本轮标准和正式应用已获确认；没有把该确认当作对未来路由效果的评价。
- 尚未验证：真实任务中的路由命中率、复盘触发率、用户满意度和文档阅读成本。

后续若要衡量任务效果，应先固定新的一组真实但脱敏的任务、评分标准与错误成本，再让改造前后版本处理同组任务。对结果做盲评，记录人工纠正次数、任务完成率和操作成本。只有在这些观察中改善，才适合进一步声称使用效果提升。
