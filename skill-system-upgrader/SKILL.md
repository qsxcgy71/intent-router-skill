# Skill 系统化改造

## 使用方式

由能够访问、编辑 Skill 文件的 Agent 执行。输入是需要改造的 Skill 路径及用户目标；路径不明确时，先从当前上下文和已安装 Skill 中定位，仅在仍有歧义时询问。

先阅读现有文件并提供简要诊断，再与用户确认标准，最后实施改造。已有明确答案不重复询问；用户尚未确认的关键标准不能用等待超时或 Agent 推断代替确认。

## 改造目标

让现有 Skill 从依赖 AI 理解和执行的操作说明，逐渐变成一套结构清晰、工具可靠、结果可验证、能够根据反馈持续改进的工作系统。尽量保留已有的有效设计，不要为了重构而重构。

## 第一步：理解现有 Skill

先定位最小相关文件集，阅读 Skill 及必要的关联文件、脚本和参考样例，梳理：

1. **工作地图（参考 Feature Map）**：任务目标、执行步骤、输入输出、依赖关系、关键分支。
2. **工具能力（参考 CLI）**：哪些操作已经有工具支持？哪些重复、确定性的步骤值得封装成工具？
3. **验证机制**：目前如何判断任务完成、结果正确？哪些要求只有文字说明，没有实际检查？
4. **反馈机制**：用户指出错误后，如何修正？能否避免同类问题再次发生？

先给出简要诊断，区分已观察事实、推断和未验证项，不立即大规模重构。

## 第二步：与用户确认验收标准

先根据现有 Skill 提出理解的标准，再向用户确认，重点覆盖：

1. **好结果是什么样的？** 哪些要求必须满足，哪些只是偏好？
2. **最不能接受什么错误？** 过去有哪些反复出现的问题？
3. **哪些环节必须人工确认？** 哪些可以放心交给 Agent 自动执行？

优先从现有文档、历史反馈和样例中寻找答案。只问缺失或模糊的关键问题，每轮最多 3 个，不让用户重新解释已有的信息。说明每个待确认事项会影响什么。用户已确认的标准和授权继续有效，不添加额外审批轮次。

## 第三步：实施改造

根据诊断和已确认标准，按需实施：

1. **结构化**：建立简洁的工作地图，让 Agent 理解任务、步骤、依赖和验收条件。
2. **工具化**：把重复、确定性的操作封装成可复用工具。需要时提供统一 CLI 入口，不强制所有 Skill 都开发 CLI。
3. **可验证**：把明确要求转化成自动检查，记录检查对象、结果和证据。内容变化后，相关验证应重新执行；语义、审美等主观判断保留人工复核。
4. **可改进**：建立反馈记录，优先把错误转化为认可样例、程序检查或工具修复，必要时再更新 Skill 说明。区分单次要求与长期规则，避免规则无限膨胀。

优先复用现有工具和验证入口。尚无重复需求或可靠判定条件时，不为了架构完整增加 CLI、数据库或自动化。

## 第四步：测试与交付

- 使用已有样例进行回归测试，条件允许时再增加真实任务测试。
- 对比改造前后的结果，确保原有重要功能没有退化。记录测试命令或评估方式、检查对象及其版本或指纹、结果和证据位置；内容改变后，旧结果不能证明新内容通过。
- 未经用户确认，不覆盖重要原始文件或正式交付结果。可以先保存独立候选、差异和证据，供用户审阅；按既有授权执行已确认的替换。
- 明确区分四类验证状态，不互相替代：

| 状态 | 所需依据 |
|---|---|
| 自动验证通过 | 实际执行的程序检查通过，保存检查对象和结果证据 |
| AI 评估通过 | AI 根据标准审阅样例或结果，记录判断依据与局限 |
| 人工确认通过 | 用户明确确认的标准或具体结果，标明确认范围 |
| 尚未验证 | 未执行、证据不足、或检查对象改变后尚未重跑 |

检查失败必须明确标记失败，不归入任何“通过”。同一成果可有多个维度的状态，例如自动检查通过但人工验收尚未验证。

最后简要说明：

1. 改造了什么，为什么？
2. 哪些问题现在可以自动检查？
3. 哪些问题仍然需要人工判断？
4. 以后用户提出反馈时，如何进入下一轮改进？

## 核心原则

- 优先解决真实问题，不追求复杂架构。
- 优先修改工具、检查和好样例，而不是不断增加提示词。
- 没有证据，不宣称验证通过。
